## 0. Целевая архитектура по ТЗ

```
 docker-compose
 ┌───────────────────────────┐   HTTP   ┌────────────────────────────┐
 │ app  (Java 11, Spring Boot│ ───────▶ │ solver (Python, FastAPI)    │
 │ 2.6.3, springdoc 1.7.0)   │          │ app/case/*: расчёт по       │
 │ · публичный API + Swagger │ ◀─────── │ приложению, валидатор       │
 │ · потоковая загрузка → диск│  JSON   └────────────────────────────┘
 │ · проекты/задания в БД    │                     │
 │ · раздача фронтенда       │              общий том /data
 └─────────────┬─────────────┘   (input.geojson, output.geojson, summary.json)
               │ JDBC
       ┌───────▼───────┐
       │ db (PostgreSQL)│
       └───────────────┘
```

Разделение обязанностей:

| Что | Где | Почему |
|---|---|---|
| Приём файла до 3 ГБ потоком на диск, учёт проектов и заданий, 50 пользователей, Swagger | Java | Это и есть «приложение» по §3.2 ТЗ |
| Расчёт трассировки, Ду, спецпроходов, стоимости, выгрузка GeoJSON | Python | Геостек (shapely, rasterio, scikit-image) и скорость доводки алгоритма |
| Проверка выхода по правилам приложения (валидатор) | Python | Та же геометрия |
| Карта и панели | React + MapLibre, статика из Java | Один фронтенд для обоих бэкендов |

**Контракт solver ↔ app.** Java вызывает
`POST http://solver:8010/api/v1/solve-file` с `{input_path, output_path, mode,
max_variants, effort, name}` — пути на общем томе; ответ — `{status,
output_path, summary}`. Паспорт входа — `POST /inspect-file {input_path}`,
протокол валидатора — `POST /validate-file {input_path, output_path}`
(Java кэширует его в `validation.json` рядом с результатом). Таймаут и
повтор держит Java. Публичный API приложения повторяет форму Python-API
(`backend/app/case/api.py`): `POST /api/v1/projects` (multipart),
`POST /api/v1/projects/{id}/solve`, `GET /api/v1/jobs/{id}`,
`GET /api/v1/jobs/{id}/summary`, `GET /api/v1/jobs/{id}/output.geojson`,
`GET /api/v1/jobs/{id}/validation`. Поэтому фронтенд разрабатывается против
Python-сервиса и без правок переезжает на Java — проверено вживую на
конкурсном наборе (сборка Maven, H2 вместо PostgreSQL на машине без Docker).

**Хранилище.** Таблицы `projects(id, name, created_at, input_path, stats
jsonb, issues jsonb)` и `jobs(id, project_id, mode, max_variants, status,
created_at, started_at, finished_at, error, output_path, summary jsonb)`;
файлы — на томе `/data/projects/{id}/`. Python-сервис держит ту же структуру в
файлах (`app/case/jobs.py`) — это и спецификация для Java, и автономный режим
без БД для разработки.

**Что не переносится на Java:** сам расчёт. Аргумент для защиты — расчётное
ядро вынесено в отдельный сервис так же, как в архитектуре ДИТ вынесен
OpenSearch; приложение, API, хранилище и развёртывание — по ТЗ.

## 1. Форма продукта

Веб-сервис. Пользователь — инженер теплосетевой организации или градостроитель.
Сценарий: открыл район → указал перспективное здание → получил варианты трассы с
расчётом → выгрузил в CAD и в проект техусловий.

Ограничения среды (см. корневой README): **Docker отсутствует**, всё поднимается
локально двумя командами. Windows — основная платформа разработки, значит никаких
зависимостей, которые собираются из исходников.

> **PostGIS сознательно не берём.** Весь расчёт идёт по одному району в оперативной
> памяти; пространственный индекс даёт Shapely `STRtree`. БД нужна только для
> метаданных проектов, но по факту и они не понадобились: район читается из
> каталога, результат кэшируется в памяти процесса. БД в проекте нет.

### Frontend

| Компонент | Выбор | Комментарий |
|---|---|---|
| Каркас | React 19 + TypeScript + Vite | |
| Карта и 3D | MapLibre GL JS | без deck.gl — см. ниже |
| Состояние | хуки React | TanStack Query и Zustand не понадобились: один экран, три запроса |
| Стили | своя таблица стилей | вместо Tailwind — на один экран стилей меньше зависимостей |

**deck.gl не нужен.** 3D-режим — это тот же слой зданий MapLibre, переключённый в
`fill-extrusion` с высотой `этажность × 3`. Это и есть «низкополигональные модели
зданий» из условия кейса: ни отдельной библиотеки, ни отдельных данных, ни
отдельного приложения. Переключение 2D/3D не меняет ни источники, ни запросы —
только `visibility` двух слоёв и наклон камеры.

**Стиль карты пустой, без внешних тайлов**: все слои приходят из нашего API. Карта
работает офлайн и на защите не зависит от сети.

### Грабли MapLibre, на которые уже наступили

**Vite ломает web worker MapLibre — карта пуста без единой ошибки.** Самый
дорогой баг проекта. MapLibre поднимает воркер через
`new Worker(new URL('./worker.js', import.meta.url))`; предбандлинг зависимостей
(`optimizeDeps`) ломает разрешение этого пути — воркер стартует пустым и молча
не отвечает на сообщения. Внешне:

- WebGL исправен, контекст не потерян, канвас нужного размера;
- стиль загружен, все слои и источники зарегистрированы;
- камера стоит над данными, источники заполнены;
- **но `source.loaded() === false` у каждого источника, включая пустые**;
- в консоли пусто.

Причина в том, что GeoJSON парсится именно в воркере. Лечится одной строкой:

```ts
optimizeDeps: { exclude: ["maplibre-gl"] }
```

плюс очистка `node_modules/.vite`. Признак, что фикс подействовал: в ресурсах
страницы появляется `/node_modules/maplibre-gl/dist/maplibre-gl-worker.mjs`.
В продакшн-сборке воркер встраивается base64 и работает без этой настройки.

> **Как отлаживать в следующий раз.** Первым делом проверять
> `map.getSource(id).loaded()` для каждого источника. Если `false` у всех —
> включая заведомо пустой — это воркер, и дальше можно не искать.
> Я потратил на этот баг несколько часов, потому что сначала списал пустую карту
> на то, что вкладка была скрыта (см. ниже) — правдоподобное, но неверное
> объяснение, которое отлично воспроизводилось в автоматизации.

**Vite слушает только на `::1`.** Браузер, резолвящий `localhost` в `127.0.0.1`,
получает `ERR_CONNECTION_REFUSED`. Лечится `server.host: true`.

**Размер во flex-контейнере.** На момент инициализации размер контейнера ещё не
посчитан, и канвас остаётся 400×300. Лечится явным `map.resize()` при настройке
плюс `ResizeObserver` на контейнере.

**Скрытая вкладка блокирует инициализацию целиком.** Если вкладка свёрнута или
не на переднем плане, браузер не выдаёт ей кадров: `requestAnimationFrame` не
вызывается, и MapLibre **не доходит даже до загрузки стиля** — `isStyleLoaded()`
остаётся `false`, `getStyle()` возвращает `undefined`, источники и слои не
добавляются. Событие `load` при этом не наступает никогда, потому что оно ждёт
первой отрисовки. Инициализация переведена на `styledata` (он не зависит от
кадра), но это лишь смягчает: если кадров нет совсем, не помогает ничто.

Практическое следствие: **проверять карту через автоматизацию браузера нельзя** —
вкладка там неактивна, кадров нет, и пустая карта выглядит одинаково при рабочем
и сломанном приложении. Отсюда правило: судить о карте по `source.loaded()` и
`queryRenderedFeatures()`, а не по скриншоту, либо смотреть живыми глазами.

Поэтому добавлен **watchdog**: если через 8 секунд карта не инициализировалась,
в интерфейсе появляется сообщение с причиной. Пустая карта без объяснения — худший
из возможных отказов, отлаживать его по скриншоту невозможно.

**Слои добавляются по одному в `try/catch`.** Невалидный стиль слоя не роняет
приложение — MapLibre просто не добавляет слой, и карта молча остаётся пустой.
Теперь падение конкретного слоя видно в интерфейсе и в консоли.

**Валидатор стилей без браузера** — `frontend/scripts/validate-style.mjs`
(`npm run validate:style`). Источники и слои живут в `frontend/src/mapStyle.ts` —
модуле без обращений к браузеру; скрипт импортирует его напрямую (Node ≥ 22.6,
стрип типов) и гоняет через `@maplibre/maplibre-gl-style-spec`, заодно сверяя
ссылки на источники, кликабельные слои и значки.

**`map.addImage()` синхронно порождает `styledata`.** Если инициализация
висит на `styledata` и добавляет значки, обработчик входит сам в себя и каждый
источник пытается добавиться дважды («Source already exists»). Слушатель
снимается до добавления значков. Проверять стили в браузере, который
не отрисовывает кадры, невозможно; этот скрипт даёт ответ за секунду.

```
   OSM / GeoJSON ──▶│  ingest      импорт, нормализация   │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  domain      единая модель района   │
                    └──────────────┬──────────────────────┘
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
      ┌───────────────┐   ┌────────────────┐   ┌────────────────┐
      │ loads         │   │ hydraulics     │   │ geo            │
      │ нагрузка Q    │   │ G, Ду, v, ΔP   │   │ проекции,      │
      │ по геометрии  │   │ резервы        │   │ растеризация   │
      └───────┬───────┘   └───────┬────────┘   └───────┬────────┘
              └───────────────────┼────────────────────┘
                                  ▼
                    ┌─────────────────────────────────────┐
                    │  costfield   поле стоимости         │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  routing     волна, трассы,         │
                    │              спрямление, варианты   │
                    └──────────────┬──────────────────────┘
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
      ┌───────────────┐   ┌────────────────┐   ┌────────────────┐
      │ compliance    │   │ economics      │   │ export         │
      │ нормоконтроль │   │ смета, риски   │   │ GeoJSON/DXF/PDF│
      └───────────────┘   └────────────────┘   └────────────────┘
```

Правила границ:

- **`routing` не знает про нормативы.** Он получает готовое поле стоимости и
  запретов. Всё знание о СП живёт в `compliance` и попадает в поле через `costfield`.
- **`compliance` работает по векторной трассе, а не по растру.** Растр — для поиска,
  вектор — для проверки. Проверять по растру значило бы проверять собственную
  дискретизацию, а не реальные расстояния.
- **`hydraulics` — чистые функции.** Ни геометрии, ни БД: на входе числа, на выходе
  числа. Это единственный модуль, который надо покрыть тестами по-настоящему.
- **Нормативы и расценки — только из конфигов.** В коде нет ни одного числа из СП.

## 4. Система координат

Вход и выход API — **EPSG:4326** (WGS84), потому что так говорят все клиенты и OSM.
Весь расчёт — в **метрической проекции**, потому что в градусах нельзя ни буфер
построить, ни длину посчитать.

Для Москвы берём **EPSG:32637 (UTM 37N)**. Искажение длин в пределах города —
доли процента, для трассировки несущественно. МСК-77 точнее, но требует
дополнительных параметров датума и на демо ничего не добавляет.

Проекция выбирается один раз на проект и хранится в его метаданных: при подстановке
данных другого города меняется одна строка конфига, а не код.

## 5. Модель данных

Ядро — `AreaModel`, всё, что нужно для расчёта по одному району, в памяти.

```python
@dataclass
class AreaModel:
    crs: str                       # "EPSG:32637"
    bounds: Polygon                # рабочая область в метрах
    buildings:   list[Building]
    heat:        HeatNetwork
    utilities:   list[Utility]     # вода, канализация, газ, кабели, связь
    roads:       list[Road]
    railways:    list[Railway]
    surfaces:    list[SurfacePatch] # покрытия: асфальт, плитка, газон, грунт
    greenery:    list[Greenery]     # деревья, кустарники
    parcels:     list[Parcel]       # участки, собственность, ЗОУИТ
    water:       list[WaterBody]
```

Ключевые сущности:

```python
@dataclass
class Building:
    id: str
    geom: Polygon                  # контур
    floors: int
    height_m: float | None
    use: BuildingUse               # жилое / общественное / промышленное
    is_perspective: bool
    load: HeatLoad | None          # Гкал/ч: отопление, вентиляция, ГВС
    entry_point: Point | None      # точка ввода (ИТП); по умолчанию — ближняя грань

@dataclass
class HeatNetwork:
    nodes: list[HeatNode]          # источник / камера / ЦТП / узел
    edges: list[HeatEdge]

@dataclass
class HeatEdge:
    id: str
    geom: LineString
    du_mm: int
    laying: Laying                 # канальная / бесканальная / надземная
    schedule: TempSchedule         # 150/70, 130/70, 95/70
    capacity_reserve_gcal_h: float # свободная пропускная способность
    head_available_m: float        # располагаемый напор

@dataclass
class Utility:
    kind: UtilityKind              # WATER / SEWER / STORM / GAS / POWER / COMM
    geom: LineString
    pressure_class: str | None     # для газа: <=0.3 / 0.3-0.6 / 0.6-1.2 МПа
    voltage_kv: float | None       # для кабелей
```

Правило: **`geom` внутри модели всегда в метрической проекции.** Перепроецирование
происходит ровно в двух местах — на входе `ingest` и на выходе `export`.

## 7. API

Версионированный REST, `/api/v1`.

| Метод | Путь | Назначение | Статус |
|---|---|---|---|
| `POST` | `/projects` | **Приём геоданных:** ZIP или набор GeoJSON → район + протокол импорта | ✅ |
| `DELETE` | `/projects/{name}` | Удалить загруженный район | ✅ |
| `GET` | `/upload/layers` | Какие слои нужны и как их можно называть | ✅ |
| `GET` | `/projects` | Список районов из `data/cache/` | ✅ |
| `GET` | `/projects/{name}` | Метаданные, статистика по слоям, перспективные здания | ✅ |
| `GET` | `/projects/{name}/layers/{layer}` | Слой в GeoJSON (WGS84) для отрисовки | ✅ |
| `GET` | `/projects/{name}/buildings` | Список зданий с нагрузкой, `?perspective_only=` | ✅ |
| `POST` | `/projects/{name}/solve` | **Главная ручка.** `?building_id&laying&resolution&diversify` → варианты | ✅ |
| `GET` | `/projects/{name}/export` | `?variant_id&format=geojson\|dxf\|pdf` | ✅ |
| `POST` | `/projects/{name}/validate` | Проверить трассу, поправленную руками, и сравнить с расчётной | ✅ |
| `GET` | `/normatives` | Нормативный профиль — чтобы UI показал, откуда цифра | ✅ |

Результат расчёта кэшируется по набору параметров (`lru_cache`), поэтому экспорт
не пересчитывает то же самое заново — он достаёт вариант из уже посчитанного
набора. Отсюда требование: параметры в ссылке на экспорт обязаны совпадать с
параметрами `solve`, иначе id варианта может не совпасть. Загрузка и удаление
района сбрасывают оба кэша.

### 7.1. Приём геоданных

Формулировка кейса начинается словами «на основе обработки массива геоданных» —
значит массив должен приниматься сервисом, а не подкладываться в каталог руками.

`POST /projects` берёт ZIP-архив либо набор отдельных GeoJSON и делает четыре вещи:

1. **Распознаёт слои по словарю синонимов.** Выгрузка почти никогда не называется
   так, как ждёт код: `Здания.geojson`, `УДС.geojson`, `Тепловые сети.geojson`,
   `Кадастр.geojson` — всё это опознаётся. Сопоставление без учёта регистра,
   разделителей и языка; неопознанные файлы не выбрасываются молча, а
   перечисляются в ответе.
2. **Выводит охват и метрическую проекцию из самих данных.** Исходная система
   координат объявляется полем `crs`; метры под видом градусов отклоняются
   с внятным сообщением, а не дают `nan` внутри расчёта.
3. **Сразу разбирает загруженное** и возвращает протокол импорта: сколько
   объектов дошло до модели по каждому слою, что отброшено и почему. Если нет
   слоёв, без которых расчёт невозможен, район удаляется, а в ответе — какие
   имена файлов ожидались.
4. **Защищается от враждебного архива:** обход путей (`../../etc/passwd`),
   абсолютные пути, распаковочные бомбы, лимиты на размер и число файлов,
   белый список расширений. Всё покрыто тестами.

Обязательных слоёв два — застройка и тепловые сети. Остальные необязательны, и
их отсутствие деградирует расчёт предсказуемо: без улиц пропадает
дифференциация покрытий, без зелени — проверка отступов до деревьев. Это видно
в протоколе, а не проявляется молча.

**`solve` синхронный, а не асинхронный.** В проекте закладывалась очередь задач с
опросом статуса, но замер показал 2–3 с на все варианты, из которых основное —
волна Дейкстры. Ради этого городить task-registry незачем: меньше движущихся
частей на защите. Район кэшируется в памяти между запросами (`lru_cache`), поэтому
повторный расчёт не перечитывает GeoJSON. Если районы вырастут настолько, что
расчёт перевалит за десяток секунд, фоновая задача появится здесь же.

Порт бэкенда — **8010**, а не 8000: на машине разработки 8000 оказался занят.
Фронтенд ходит по относительным `/api/...`, Vite их проксирует, так что CORS в
разработке не участвует вовсе (middleware оставлен на случай раздельного деплоя).

## 9. Производительность

Бюджет — **весь расчёт трёх вариантов не дольше 10 секунд**, иначе это не
интерактивный сервис.

| Этап | Оценка |
|---|---|
| Растеризация слоёв в поле стоимости, 2×2 км при шаге 1 м (4 млн ячеек) | ~0,5 с |
| Одна волна Дейкстры по полю (`MCP_Geometric`) | 1–3 с |
| Спрямление и нормоконтроль векторной трассы | < 0,1 с |
| Гидравлика, смета | пренебрежимо |

Главный рычаг — **поле стоимости строится один раз на задачу**, а три профиля
получаются модификацией множителей на уже растеризованных масках, без повторной
растеризации. Волна Дейкстры от здания тоже одна на профиль (см. `04-algorithm.md`),
а не по одной на каждого кандидата врезки.

Рабочая область — не весь город, а bbox вокруг здания и кандидатов подключения с
запасом. Если ближайшая сеть далеко, область растёт, шаг сетки увеличивается до 2 м.

## 10. Что решено и что осталось открытым

**Решено:**
Python + FastAPI без Docker · расчёт и состояние целиком в памяти процесса,
БД не появилась вовсе · UTM по зоне района · растровое поле стоимости +
`MCP_Geometric` · нормативы только из конфигов · нормоконтроль по вектору,
не по растру · MapLibre без deck.gl, 3D тем же слоем.

**Открыто, решается при реализации:**

- Формат хранения кэша слоёв — GeoJSON или Parquet (зависит от объёма выгрузки OSM).
- Нужен ли `rasterio`: если растеризация упрётся в установку GDAL на Windows,
  переходим на `skimage.draw` с ручной обработкой дыр в полигонах.
- Ортогонализация трассы (§9.4 в `04-algorithm.md`) — делаем ли в MVP или в стретч.
- DXF-экспорт — какие слои и блоки ждёт CAD-специалист; уточняется по образцу.
